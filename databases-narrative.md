Database Improvements and Examples:
	I added read_page in CRUD_Python_Module.py. It takes in a search filter, page number, page size, and a list of fields that need to be returned. The filter shows what animals qualify under the criteria of the rescue categories. The method can support fields separately or together, meaning it can be reused beyond the rescue buttons. For example, a request can search for dogs of a certain breed, sex, and within an age range. This goes beyond the original use of search dictionaries while putting in checks around the requests.
	Database pagination now requests one page at a time. The dashboard uses 10 animals per page. My saved Water Rescue comparison got 17 matching animal records. Those results fit in 2 pages, 10 animals on the first and 7 on the second. For page 2 the method calculates (2 – 1) x 10, skips the first 10 matches and requests ten more. MongoDB orders the results by the _id field before picking a page. 
	The method also uses projection, which is choosing what fields MongoDB returns. The dashboard needs fields like name, breed, age, and map coordinates. Another call could request only name and breed. MongoDB’s _id field is left out of the returned records since the table doesn’t really need it. In the original application, the field was removed after it was retrieved. This changed taught me to understand what information is needed before asking for it. 
	I added input validation, which is checking that a request follows the rules set. The page must be a whole number starting at 1, and the page size must be between 1 and 100. Requested fields must be from the set list. Age limits must not be a negative number in whole weeks, and the min can’t be above the max. For example, page 0 or an age range from 100 weeks to 20 weeks would raise an error. The method also rejects search fields and operators that aren’t supported instead of just passing it to MongoDB. 
	I continued the protected login used in Enhancement Two. The notebook asks for login credentials without displaying them and reads them from the environment. I added configurable connection settings and a server connection timeout. The new read method limits query execution time and replaces database errors with a message. These changes reduce exposure to sensitive data and make failed requests easier to deal with. The validation only applies to the new read method, not the other CRUD operations. 
Measured Results:
	I identified one specific index and compared query execution before and after indexing. I did this by adding one compound index called rescue_type_breed_sex_age. A compound index keeps an organized structure for multiple fields together. This index contains animal_type, breed, sex_upon_outcome, and age_upon_outcome_in_weeks, in that specific order. I chose those fields because the existing rescue categories already use them together. Compound indexes help queries that keep searching the same fields. 
	I compared the same Water Rescue request before and after creating the index. I searched for dogs under the water rescue criteria, the water rescue breeds, Intact Female, and an age from 26 to 156 weeks. Both measurements used the same returned fields, _id ordering, and first page limit of 10. The measurement code ran it three times and took the median time.

	The results are in index_before.json and index_comparison.json. The comparison code checked that the total number of matching animals and the real first page records stayed the same. MongoDB examined about 99 percent fewer animal records after the index was added. The 22 index entries are lookup entries examined. 
	The saved query plans, which showed the MongoDB steps it took, helped me understand why the work changed. Before the enhancement, MongoDB used the existing _id index and examined a lot of records to get rescue matches. After, it used the compound index to narrow the search. The later plan included a step to sort the results by _id. 
	The reported 0 ms doesn’t mean the request took no time. It is the value reported at the measurements ms. These measurements describe the database find requests, not the dashboard load time or the count request. The time records the query plan and execution but not the network transfer time. This drastic reduction shown is evidence of improvement for the tested query. Although it doesn’t prove the very search would improve the same amount. 
Challenges and Design Choice:
	One challenge was updating the original map after reducing the returned fields. The old map used column positions, like columns 13 and 14, to find coordinates. Returning less fields meant those positions would be different. I changed the map to read location_lat and location_long by name. I added checks for a selected row that doesn’t belong to the current page and coordinates outside a specific range. This taught me that even when changing a database result, it could affect other parts of the application.
	Another challenge was connecting the database pages to the filters and merge sort. I kept the selected rescue category and current page in Dash so the callback could remember them. Selecting a different rescue category would return to page one. Previous and Next buttons request another database page, and the dashboard disables them at the first and last pages.
	Pagination changed the sorting and breed chart. The merge-sort now organizes only animals belonging to the current page. For example, choosing age order on page one arranges those 10 animals, not the 10 youngest animals across the 17 matched records. The chart also is based on the current page. This keeps the database and algorithm enhancements connected while making their differing jobs clear. 
	I considered the limits of my choices. Indexes need extra storage and maintenance when data changes, so adding more indexes doesn’t just make things better. The skip and limit pagination is simple and direct, but later pages can take more work as MongoDB skips more results. I also separate a count request to display the total. These tradeoffs help me keep changes realistic while understanding that a larger application would need to take a different approach.
